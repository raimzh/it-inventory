# IT Inventory

Корпоративный учёт основных средств: карточки техники, инвентаризация со
сканером, склад расходников, обмен с 1С, отчёты и печать наклеек.

Работает на месте (Windows + PM2), доступен по локальной сети — в том
числе с терминалов сбора данных, которые ходят на него как на обычный
сайт.

---

## Из чего состоит

| Часть | Что внутри | Порт |
|---|---|---|
| `backend/` | NestJS 11, TypeORM, PostgreSQL | 3001 |
| `frontend/` | Next.js 16 (App Router), React 19, Tailwind 4 | 3000 |

Браузер ходит **только** на фронтенд. Запросы к API идут через прокси
`frontend/src/app/api/[...path]/route.ts`: он подставляет заголовок
`Authorization` из httpOnly-куки, поэтому токены не видны JavaScript'у
в браузере. Бэкенд при этом остаётся на обычных Bearer-токенах — с ним
можно работать напрямую из тестов и интеграций.

### Роли

| Роль | Что может |
|---|---|
| `admin` | всё, включая пользователей и резервные копии |
| `accountant` | учёт, инвентаризация, отчёты, выгрузки, обмен с 1С |
| `inventorizer` | инвентаризация и склад; отчёты видит, выгружать не может |
| `viewer` | только просмотр карточек; инвентаризация и отчёты закрыты |

## Запуск для разработки

Нужны Node 20+ и PostgreSQL.

```bash
npm --prefix backend install
npm --prefix frontend install
```

Скопируйте `.env.example` в `backend/.env` и заполните — как минимум
`DB_PASSWORD` и `JWT_SECRET`, без них приложение не стартует (см.
[Переменные окружения](#переменные-окружения)).

```bash
npm run dev
```

Поднимет оба процесса сразу. По отдельности:

```bash
npm --prefix backend run start:dev
npm --prefix frontend run dev
```

Документация API — `http://localhost:3001/api/docs`.

## Переменные окружения

Полный список с пояснениями — в `.env.example`. Здесь только то, без
чего не обойтись.

**Обязательные.** Приложение падает на старте с внятным сообщением,
если их нет:

| Переменная | Требование |
|---|---|
| `DB_PASSWORD` | — |
| `JWT_SECRET` | не короче 16 символов, не из списка известных заглушек |

Значений по умолчанию у секретов нет намеренно: дефолт вроде
`supersecretjwtkey` попадает в репозиторий и становится публично
известным, а приложение с ним молча запускается и выглядит рабочим.

Сгенерировать секрет:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

**Стоит задать на боевом стенде:**

- `PG_DUMP_PATH` — на Windows каталог PostgreSQL обычно не в `PATH`, и
  без явного пути резервная копия не создаётся вовсе.
- `BACKUP_ENCRYPTION_KEY` — дамп содержит всю базу, включая хеши
  паролей; в открытом виде он опаснее самой базы. **Потеря ключа =
  потеря всех копий**, храните отдельно от них.
- `BACKUP_MIRROR_DIR` — второе расположение для копий. Без него они
  лежат рядом с базой и пропадут вместе с машиной.
- `ADMIN_USERNAME` / `ADMIN_PASSWORD` — учётка администратора создаётся
  при первом запуске. Не заданы — сид пропускается.

## Миграции

```bash
npm --prefix backend run build          # миграции берутся из dist/
npm --prefix backend run migration:run
npm --prefix backend run migration:show
npm --prefix backend run migration:revert
```

`RUN_MIGRATIONS=true` применяет их при старте приложения — годится,
когда пользователь БД владеет схемой. Если роль приложения без прав
DDL, оставьте пусто и прогоняйте вручную привилегированной ролью.

## Тесты

Фронтенд — чистые модули, база не нужна:

```bash
npm --prefix frontend test
```

Бэкенд разделён на две части. Разбор дат, кодов этикеток и штрихкодов
не требует ничего:

```bash
npm --prefix backend run test:import
```

Остальные наборы бьют по **запущенному экземпляру** через HTTP и пишут
в базу:

```bash
npm --prefix backend run test:auth       # вход, обновление и отзыв токенов
npm --prefix backend run test:inventory  # ход инвентаризации
npm --prefix backend run test:backup     # резервные копии
npm --prefix backend run test:sync       # обмен с 1С
npm --prefix backend run test:reports    # отчёты и выгрузка
npm --prefix backend run test:users      # уборка учётных записей
npm --prefix backend run test:e2e        # сквозные проверки API
npm --prefix backend test                # складские движения
```

Им нужны запущенное приложение (`BASE_URL`, по умолчанию
`http://localhost:3009`) и `ADMIN_PASSWORD` в окружении.

### Против боевой базы они не запустятся

Это защита, а не неудобство. Прогон на рабочей машине с боевой
конфигурацией оставлял в учёте фикстуры — за месяц накопились 48
тестовых ОС, позиции склада и учётка, которую держал журнал аудита.
Теперь наборы, пишущие в базу, проверяют имя базы и адрес приложения и
отказываются работать:

```
Тест пишет в базу и остановлен, чтобы не засорить учёт:
  • база «it_inventory» не похожа на тестовую (ожидается имя с _test)
```

Чтобы гонять локально, заведите отдельную базу (нужна роль с правом
создания БД — учётка приложения им не обладает):

```sql
CREATE DATABASE it_inventory_test OWNER itinv_app;
```

и запускайте с `DB_NAME=it_inventory_test`. Осознанный обход —
`ALLOW_PROD_DB=1`; он оставлен намеренно, но это должно быть решением,
а не забывчивостью.

В CI база отдельная (`it_inventory_test`) и одноразовая, поэтому там
ничего не копится.

## Боевой стенд

Оба процесса живут в **системном** экземпляре PM2
(`PM2_HOME=C:\ProgramData\pm2-ktms`), поэтому все команды PM2 требуют
**прав администратора**. Без них `pm2` возвращает `EPERM` и процессы
молча продолжают работать на старом коде.

Пересборка и перезапуск — одной командой, из окна PowerShell,
запущенного от имени администратора:

```bash
powershell -ExecutionPolicy Bypass -File "C:\Users\zhuma\projects\it-inventory\redeploy.ps1"
```

Скрипт сам проверяет права и откажется работать без них.

Вручную:

```bash
npm --prefix backend run build
npm --prefix frontend run build
pm2.cmd restart it-inventory-backend it-inventory-frontend --update-env
```

Правки только во фронтенде не требуют перезапуска бэкенда, и наоборот.

### Доступ по локальной сети

Приложение слушает `0.0.0.0:3000`, но профиль сети Windows обычно
«Общедоступная», и входящие подключения закрыты. Нужно правило
брандмауэра на TCP 3000 из локальной подсети. Терминалы заходят на
`http://<адрес-сервера>:3000`.

> **Трафик идёт открытым текстом.** TLS не настроен: блок HTTPS в
> `nginx/nginx.conf` закомментирован, а PM2 отдаёт голый HTTP. Флаг
> `Secure` у кук поэтому не ставится, и пароль при входе вместе с
> refresh-токеном (живёт 7 дней) виден любому, кто слушает тот же
> Wi-Fi. Пока это так, сеть с терминалами должна считаться доверенной.

## Наклейки и сканер

Инвентарные наклейки печатаются на этикеточном принтере Zebra через
обычный драйвер Windows — по одной с карточки ОС или пачкой из списка
(кнопка «Наклейки»). Макет настраивается прямо в окне печати и
сохраняется на устройстве: у рулонов разный размер, у принтера своя
непечатаемая кромка.

Штрихкод — Code 128 с инвентарным номером, генерируется своим модулем
(`frontend/src/lib/code128.ts`). Не QR: сканеры уже читают линейный код
со старых наклеек, и новые должны читаться так же.

Терминал сбора данных работает как клавиатура. Распознавание отличает
скан от набора руками по скорости ввода
(`frontend/src/lib/scan-buffer.ts`). Если сканер не читается, есть
отладочная страница **`/scan`** — открывается без входа в систему и
показывает, что именно прислало устройство: сырые нажатия, интервалы,
распознанный код.

Номера ищутся и в том виде, как напечатаны, и без ведущих нулей: на
старых наклейках номер дополнен до девяти знаков (`000009079`), а в
учёте лежит как `9079`.

## Полезное

- `redeploy.ps1` — пересборка и перезапуск боевого стенда.
- `scripts/kill-ports.ps1` — освободить занятые порты перед `npm run dev`.
- `backend/scripts/decrypt-backup.js` — расшифровать копию `.sql.enc`.
- CI (`.github/workflows/ci.yml`) прогоняет линт, сборку, миграции
  (включая откат и повторное применение) и все тесты на каждый push.
